# Portfolio page output

Use this when the user asks for a portfolio page, not only a review. The page builds on the review: the same evidence rules apply.

Everything on the page belongs to the page's owner, the person whose GitHub profile or repository is under review. Every line, figure, video, link and contact detail comes from the owner or from the owner's own sources. Do not add the name, links, results, events or contact details of this plugin's author or of any other third party.

## Ask the owner first

Before writing the page, ask the owner for anything on this list that the owner's sources do not state:

- The opening line, in the owner's own words. Offer a draft in the "I help [who] [get what result]" pattern when the owner has no line yet, and use the draft only after the owner approves the wording.
- Up to three headline results, each with a source you can open.
- The next step the owner wants a reader to take (for example a contact page, a booking link or an email address).

## Order, top to bottom

1. **Opening line.** Use the owner's approved line word for word.
2. **Hero stats.** A bold section with up to three big stat callouts, stated once, here only. Each figure needs a source you opened this run. Do not repeat these figures elsewhere on the page. Leave the section out when the owner has no sourced figures.
3. **Lead video or image.** When the owner has a video or image that shows the main result, place the video or image right under the hero.
4. **The projects, one card each.** Never a single grouped highlight. Frame each card as proof of the hero result. Each card has:
   - A title and what the project handles, in one or two plain sentences.
   - A link to the project (repository, public guide or demo).
   - A video when the owner's project has one: `<video autoplay muted loop playsinline preload="metadata" poster="...">`, with the poster as the fallback image, plus a "Watch the video" link to the same file. When no video exists, use a screenshot or image from the owner's repository. When neither exists, leave the media out. Reference real files only.
   - Time saved, only when a source states the figure. If none is stated, leave time saved out. Never estimate.
5. **Other work.** Talks, workshops, writing or teaching go in a short section after the cards, only when the owner's sources show the work. Feature at most two items.
6. **Closing next step.** Repeat the owner's chosen next step.

## Patterns that make portfolios stand out

Researched Nov 2, 2026. Apply these on every page:

- **Clear in the first screen.** Who the owner is, what the owner does and the result should be visible without scrolling ([ReadmeDesign](https://readmedesign.com/showcase)).
- **Story first, proof second.** Open with the personal line, then the stats ([ReadmeDesign examples](https://readmedesign.com/blog/best-github-profile-readme-examples)).
- **Real, sourced proof near the top.** Use only figures from a source you opened this run. Don't add ratings, review counts or revenue unless a source you can read states them or the owner confirms them in this conversation.
- **Same structure on every card.** Start with the result in the title. Add one sentence on what the project handles, the media and links to the process or code ([GitHub Docs](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume), [Pranjul Rathour](https://pranjulrathour.github.io/blog/github-profile-that-recruiters-read/)).
- **One clear next step.** Put the owner's chosen next step in the hero and again at the end ([Forbes](https://www.forbes.com/sites/jodiecook/2026/09/08/turn-your-linkedin-profile-into-a-machine-that-sells-for-you/), [Blueberry Media](https://blueberry-media.co.uk/blog/linkedin-profile-optimisation-b2b-clients)).
- **Match LinkedIn.** When the owner shares a LinkedIn headline, keep the opening line and the stats consistent with the headline ([Resumeily](https://www.resumeily.com/learning/how-to-write-a-linkedin-profile)).
- **Easy to skim.** Use short lines and no badge walls.

## Rules

- No em dashes anywhere. Before any of these conjunctions (and, or, but, so, yet, nor, for), keep the comma only when both sides are full clauses with their own subject.
- Dollar amounts inside video scripts or sample data are examples. Never use them as results.
- Don't show private repo contents on a public page. Link private code only when the reader has access; otherwise link a public guide.
